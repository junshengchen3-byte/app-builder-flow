# app-builder-flow

`app-builder-flow` 是一个用于 App 产品开发流程的 Codex Skill。它帮助把一个 App 想法或现有 App 项目推进到可执行、可测试、可发布的方案。

它不是某一个具体 App 的模板，也不是提词器 App 本体。它适用于 iOS、Android、Web/PWA、SaaS、内部工具等 App 产品规划和开发推进场景。

## 项目解决什么问题

很多 App 项目一开始容易直接进入页面或代码实现，导致这些问题：

- 目标用户和核心场景没有确认清楚。
- MVP 范围过大，第一版迟迟不能完成。
- UI、数据、权限、测试和发布准备彼此脱节。
- 过早引入登录、云同步、支付、AI 或后端，增加不必要复杂度。
- 遇到卡点时只停留在问题描述，没有明确原因和处理方式。

`app-builder-flow` 解决的是“从 App 想法到可发布版本”的流程问题：先锁定产品决策，再拆分实现路径，最后按阶段推进测试和发布准备。

## 主要功能

- 产品澄清：确认目标用户、使用场景、核心问题、平台和版本目标。
- MVP 定义：区分第一版必须功能、延后功能和明确不做的功能。
- 页面与交互规划：梳理首页、核心路径、设置页、空状态、异常状态和权限时机。
- 技术路线判断：根据实际需求选择原生 App、跨平台、Web/PWA、后端、数据库和部署方式。
- UI 方向推进：结合用户参考图、品牌风格、组件密度和交互规则形成可执行方向。
- 实现阶段拆分：优先推进最小可用闭环，再逐步补齐功能。
- 测试与验收：覆盖自动化测试、手动路径、权限拒绝、数据持久化和设备适配。
- 发布准备：整理应用名称、图标、截图、隐私说明、签名、构建、TestFlight 或商店提交材料。
- 卡点处理：每个阶段说明阻塞原因、影响范围、负责人和处理方式。

## 安装方法

项目内 Skill 位于：

```text
skills/app-builder-flow/
├── SKILL.md
├── agents/openai.yaml
└── references/
    ├── discovery-questions.md
    ├── implementation-output.md
    ├── release-checklists.md
    └── stage-gates.md
```

如果只是本地维护这个 Skill，不需要额外安装。

如果要让 Codex 在本机可发现并使用这个 Skill，可以把 `skills/app-builder-flow` 复制到 Codex 的 skills 目录。不同环境的 Codex skills 目录可能不同，请以当前 Codex 环境说明为准。

安装后建议运行 Skill 校验：

```bash
quick_validate.py skills/app-builder-flow
```

如果当前环境没有直接暴露 `quick_validate.py`，请使用 Codex Skill Creator 自带的校验脚本运行同一个目录。

## 使用方法

在 Codex 中明确调用：

```text
使用 app-builder-flow，帮我把一个 App 想法推进成可开发方案。
```

也可以用于已有 App 项目：

```text
使用 app-builder-flow，帮我梳理这个 App 下一步开发、测试和发布准备。
```

典型流程：

1. 先确认产品、用户、平台、MVP 和不做什么。
2. 输出摘要、核心功能、页面流程、数据与接口、失败处理、测试验收和默认决定。
3. 用户确认后进入 UI、实现、测试或发布阶段。
4. 每一步说明已完成内容、当前卡点和处理方式。

不适用场景：

- 单纯改文章、改标题、润色文案。
- 单纯创建 README。
- 单纯讲 GitHub 上传流程。
- 与 App 产品定义、实现、测试或发布无关的仓库整理。

## 输入输出示例

### 示例一：iOS App

输入：

```text
我想做一个提词器 App，给短视频口播创作者用。iOS 和 iPadOS 都要支持，第一版不登录，本地存储。
```

输出：

```text
产品摘要：
面向短视频口播创作者的本地提词器 App，核心解决脚本管理、全屏提词和 App 内拍摄提词。

MVP 范围：
- 新建和编辑脚本
- 脚本列表、搜索、星标置顶
- 全屏提词
- 拍摄提词
- 本地设置

默认决定：
- SwiftUI 原生路线
- iOS / iPadOS 17+
- 不登录、不云同步、不引入后端

卡点：
- 真机相机、麦克风、相册权限需要设备验证
- App Store 发布需要开发者 Team 和签名配置
```

### 示例二：Web / SaaS

输入：

```text
我想做一个小团队用的客户跟进工具，手机和电脑都能用，需要多人共享数据。
```

输出：

```text
产品摘要：
面向小团队的客户跟进 Web/PWA，用来集中管理客户状态、跟进记录和下一步行动。

技术判断：
- 多人共享数据需要账号、权限、后端和数据库
- 手机和电脑都要用，Web/PWA 比单一原生 App 更适合第一版

下一步：
确认成员角色、客户字段、跟进流程和权限边界。
```

### 示例三：普通文章请求

输入：

```text
帮我改一篇文章标题。
```

输出：

```text
这不是 App 产品规划、实现、测试或发布任务，不进入 app-builder-flow。应直接按文章编辑任务处理。
```

## 本地验证

推荐验证项：

- 运行 Skill 结构校验。
- 用 iOS App、Web/SaaS、普通文章请求三类输入测试触发边界。
- 检查 `agents/openai.yaml` 的名称、描述和默认提示是否与 Skill 一致。
- 确认 Skill 不会把 README-only 或 GitHub-only 请求误判成完整 App 开发流程。

当前 Skill 的目标是帮助 App 项目形成清晰的产品、实现、测试和发布路径；不负责替代具体 App 的业务代码。
